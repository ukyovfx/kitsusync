# KitsuSync ↔ VFX Files Plugin integration contract v1

**Contract version:** `1.0.0`
**Status:** Draft compatibility contract for sync operations and signed events
**Authority:** The Drive ownership model in this document reflects the current cross-repository decision: the Files Plugin owns Drive configuration per Production. Older KitsuSync-owned configuration operations described below remain only as compatibility and explicit-import surfaces; they are not the active setup workflow.

## Ownership

- Kitsu/Zou owns the canonical UUIDs, names, hierarchy, membership, Tasks, Task Types, and source metadata. Names are display snapshots only; IDs are identity.
- The Files Plugin is the sole editable Drive authority per Production: OAuth connection and encrypted credentials, verified root, storage configuration, templates, activation epoch, folder bindings, sync jobs, Output Packages/manifests, and per-recipient delivery state. Plugin workers fence execution against that Production's current revision and activation epoch.
- KitsuSync consumes sanitized Plugin authority/configuration reads for status, notification fencing, and sync orchestration. It does not authorize Drive OAuth, verify or select Drive roots, write Drive configuration, or activate/deactivate the Plugin. Its local configuration row is a non-secret read mirror used for event admission and a preserved legacy source until an explicit Plugin import completes; it is not a second writer.
- KitsuSync owns Discord routing and delivery. The Plugin reports signed business events; it does not send Discord messages. `Project.StorageURL` remains the existing optional generic link and is not repurposed.
- Native Kitsu Files Plugin settings are the Drive setup surface in both standalone and integrated installations. KitsuSync obtains any required Kitsu/Zou object snapshot through its existing server-side Kitsu integration and sends that bounded, read-only snapshot to the Plugin for sync operations. Google credentials and Kitsu credentials are not copied between the systems.

## OAuth decision and Drive scope

Use the Plugin's native Kitsu Production settings and Kitsu/Zou role authorization to start OAuth. The Plugin owns the fixed callback URI, exchanges the code server-side, and stores refresh credentials encrypted in its protected credential store. OAuth state is single-use and bound to the authenticated actor and Production. KitsuSync does not receive the authorization URL, code, access token, refresh token, service identity, or internal `credential_ref`.

Retain the existing `openid` and `drive.file` scopes and server-held credentials. Initial root selection is limited to Plugin-created or demonstrably app-authorized roots that pass the existing My Drive owner and write-capability verification. Existing roots outside the app-visible grant remain blocked until a secure selection workflow is verified. Do not implement desktop/mobile One-Pick without proving web-client compatibility; do not expose browser tokens, widen scopes, or treat a supplied Drive URL as authorization. A saved KitsuSync `StorageURL` stays generic.

## Authentication and secrets

The native Kitsu session and Kitsu/Zou Production role authorize Drive configuration. The OAuth callback and code exchange terminate at the Plugin backend. KitsuSync's browser surface displays sanitized connection/root/activation status and links to native Kitsu settings. The browser never receives a Google access or refresh token, Plugin service credential, credential reference, or Drive API response containing credentials.

KitsuSync-to-Plugin calls use the standard RFC 9068 JWT access-token profile, not the event HMAC mechanism. The exact v1 profile is declared as `x-service-bearer-profile` in `plugin-api.openapi.json`:

- The token is compact JWS with `typ: at+JWT`, `alg: RS256` only, and a `kid` from the configured KitsuSync signing-key set. `none`, HMAC algorithms, algorithm negotiation, and key URLs from token headers are rejected.
- `iss` is the exact operator-configured canonical HTTPS KitsuSync origin. `aud` is the exact Plugin API server URL, including `/api/plugins/vfx_files/integrations/v1`. `sub` is the configured KitsuSync service identity and `client_id` is the installation identifier.
- Required claims are `iss`, `aud`, `sub`, `client_id`, `iat`, `nbf`, `exp`, `jti`, `scope`, `production_id`, `actor_id`, and `actor_role`. `production_id` and `actor_id` are UUIDs; `actor_role` must be `production_admin`. The token authorizes exactly one Production.
- Access tokens are valid for at most 300 seconds with 30 seconds of clock skew. Every operation declares one exact `x-required-scope`; the token's space-delimited `scope` must contain it. The Plugin checks its request Production and referenced connection/root/job/snapshot against the signed `production_id` on every call.
- Every request also carries `X-KitsuSync-Actor-ID`. It must exactly match the signed `actor_id`. KitsuSync derives the actor from its authenticated session and issues a token only after checking the actor's Production-admin permission. The Plugin rejects missing/mismatched actor identity and does not trust a stand-alone actor header.
- KitsuSync serves only public verification keys at `GET /.well-known/vfx-files-jwks.json`. The endpoint returns a bounded RS256 JWKS with `Cache-Control: public, max-age=300`; it contains no token or private key. KitsuSync publishes a new `kid` before issuing with it, keeps the old public key through the maximum token lifetime plus clock skew, and removes it after that overlap. The Plugin refreshes once for an unknown `kid`, then fails closed. Emergency key removal invalidates that key after the bounded cache lifetime.
- Invalid/missing bearer, signature, algorithm, issuer, audience, `kid`, time claim, actor claim, or malformed token returns `401`. A valid token with a missing scope, non-admin actor role, or Production/resource mismatch returns `403`. No cookie, query-parameter, unsigned-header, or unauthenticated fallback is allowed.

This JWT bearer profile applies only to KitsuSync backend → Plugin read/status and sync-operation requests. The current KitsuSync client does not allowlist the legacy OAuth authorization, revoke, root-verification, desired-config-write, or activation-write operations. They must not be restored as a setup path. Plugin → KitsuSync business-event intake remains separately authenticated using the documented HMAC signature, timestamp, nonce, raw-body SHA-256, and idempotency key; neither direction accepts the other's credentials.

The Plugin management API uses Zou's official plugin route prefix. The Plugin's `manifest.toml` ID is `vfx_files`, so its exact base is `/api/plugins/vfx_files/integrations/v1`; it does not expose or rely on a root `/api/integrations/v1` alias. The Plugin registers its relative routes beneath `/integrations/v1` through the normal Zou plugin route list. KitsuSync calls that exact base URL over HTTPS, supplied by operator configuration and matched to the JWT audience. There is no unauthenticated compatibility alias and no new public API proxy. The event-intake service remains at KitsuSync's independent `/api/integrations/vfx-files/v1/events` route.

Operation scopes are: `vfx.connections.read`, `vfx.connections.authorize`, `vfx.connections.revoke`, `vfx.roots.read`, `vfx.roots.verify`, `vfx.templates.read`, `vfx.config.read`, `vfx.config.write`, `vfx.activation.write`, `vfx.sync.preview`, `vfx.sync.apply`, `vfx.sync.read`, `vfx.sync.retry`, `vfx.sync.reconcile`, and `vfx.sync.snapshot.write`. The scope table is attached to each OpenAPI operation and the allowed set is listed in the token profile. A Google OAuth scope alone is not treated as a Production-root boundary.

The Draft stack includes the v1 event/sync contract, RS256/JWKS service authentication, native Plugin Production Drive authority, and the KitsuSync read-only consumer. The Plugin owns OAuth, credentials, root selection, templates, configuration revisions and activation epochs. KitsuSync reads sanitized Plugin authority status and a configuration mirror for event fencing, builds a bounded read-only Kitsu snapshot, uploads hashed pages, and supports idempotent Preview, Apply, job refresh, retry, and reconcile. KitsuSync does not write Drive settings. Signed event intake and exact-route Discord delivery use the existing inbox and notification journal. Focused and synthetic tests exist, but no live Files Plugin API, Google OAuth/Drive, or Discord delivery has been verified. These Draft branches are not an active or production-ready integration.

The Plugin may keep an opaque internal `credential_ref`, but it is not returned to KitsuSync or accepted from the browser. The current Plugin implementation stores encrypted credentials server-side and retains the existing OAuth scope and credential isolation boundaries. No real credentials were used during synthetic verification. Credential provisioning, rotation, and revocation must continue through the Plugin's protected server-side controls; never place tokens in KitsuSync SQLite, browser state, source control, images, or logs.

The Plugin's native Kitsu Production page owns the callback flow. OAuth state is single-use and bound server-side to the authenticated actor and Production; caller-controlled redirect URIs are rejected. The Plugin callback exchanges the code and stores credentials server-side. KitsuSync does not receive or process OAuth codes, tokens, or authorization redirects. Its former OAuth-return route rejects credential query parameters and is not part of the current setup workflow. Disconnect/revoke operations are performed in the Plugin and remain subject to durable audit and failure-state handling.

## HTTP and event delivery semantics

- `plugin-api.openapi.json` describes KitsuSync backend → Plugin backend calls.
- `kitsusync-events.openapi.json` describes Plugin backend → KitsuSync event intake. These are separate trust directions, not one shared API surface.
- Both directions use `/v1`; requests and responses carry `contract_version: "1.0"`. Additive fields are compatible within major v1. Unknown major versions fail closed with `unsupported_contract_version`.
- Commands that create or mutate a provider-side operation require an `Idempotency-Key`. Repeating a key with the same canonical body returns the original operation; reusing it with a different body returns `idempotency_conflict`. Sync Preview is read-only with respect to Drive, but creates an expiring provider Preview resource, so its POST also requires an idempotency key and retries must reuse the same key.
- Native Plugin settings write configuration with revision/epoch fencing, concurrency protection, and idempotent retries. KitsuSync does not call the legacy desired-config PUT or activation operations.
- Root selection and the existing My Drive owner verification occur inside the Plugin's native authorized workflow. KitsuSync consumes sanitized status/configuration reads and does not accept owner or root identity from browser input.
- Activation is a distinct explicit administrator action in native Plugin settings. It increments the activation epoch; KitsuSync admits/delivers events only when their positive epoch equals the current enabled Plugin mirror. Deactivation/re-activation advances the epoch so stale events cannot become newly eligible.
- The KitsuSync backend uploads a bounded read-only Kitsu object snapshot to the Plugin in pages. `source_etag` is a content-derived SHA-256 fingerprint of the exact locally assembled Kitsu snapshot because Kitsu project list endpoints do not promise a collection ETag; it is not an upstream HTTP validator. The snapshot start binds Production, config revision, source fingerprint, object count, page count and full snapshot SHA-256. Each page is idempotent and hash-checked. Completion seals an immutable snapshot only if every page and canonical digest matches. Preview is allowed only against a complete, unexpired snapshot and the matching config revision. Use RFC 8785 JSON Canonicalization Scheme bytes for each page's `page_sha256` and for the full ordered object-array `snapshot_sha256`; pages contain at most 500 objects and the whole snapshot at most 500,000. Objects are ordered by `(object_type, id)`, IDs must be unique, and every non-null parent must resolve within the same snapshot. Include ancestors as `included_in_sync:false` context when needed to render a selected object's path. A changed config/source fingerprint invalidates the preview; the Plugin does not query Kitsu itself.
- A sync Apply requires a current successful preview ID, matching Production/config revision, Plugin-verified root, and explicit administrator action. A pasted/saved URL, root candidate, or successful OAuth alone never starts folder creation.
- Sync job creation is asynchronous (`202`); the operation ID is stable and status is read through the job resource. Retry and reconcile are distinct idempotent commands. Ambiguous provider outcomes remain `reconcile_required`; the client cannot request blind replay.
- Event intake returns `202` only after each newly accepted event is durably recorded. Per-event outcomes distinguish `accepted`, `duplicate`, and `quarantined`; invalid batch structure is rejected at HTTP level. A duplicate `(producer_id,event_id)` with identical body is idempotent; same identity with different body is a security-visible conflict and is never sent.
- `folder.provisioning.completed` and `output_package.created` / `output_package.ready` are durably recorded for integration diagnostics but are not Discord delivery work. Only `file_delivery.*` events carry a recipient Task Type and can enter the existing Discord routing/journal path; no folder/package event is broadcast or assigned an inferred route.
- HMAC is calculated in constant time over `timestamp + LF + nonce + LF + lowercase raw-body SHA-256 + LF + Idempotency-Key`; the key ID selects a Plugin integration key that is bound to the producer identity. Enforce a short timestamp window and durable nonce uniqueness. The body hash covers the exact raw UTF-8 request bytes. No browser receives this integration key.
- Every post-activation business event carries `activation_epoch`. KitsuSync compares it with the current enabled Production mirror before journaling; mismatches and bootstrap discovery are quarantined/suppressed. The existing exact-next-epoch `503` transition marker was designed for KitsuSync-initiated activation and is not part of the native Plugin activation flow. The current read-only consumer refreshes the mirror on the KitsuSync settings page, while event admission and Discord dispatch read SQLite. Therefore integrated event/activation safety is not complete until a trusted, bounded Plugin status synchronization mechanism prevents stale mirrors from admitting or dispatching events after native activation changes. Do not weaken epoch comparisons or claim integrated readiness before that gate is resolved and tested.
- For a Discord `429` with a Retry-After beyond KitsuSync's bounded in-process wait, the delivery journal stores the retry deadline. The inbox remains pending and is eligible again after that deadline; KitsuSync does not age-filter or silently discard old pending events. Each processor pass traverses accepted due work through a fixed inbox high-water mark using bounded pages, so an earlier deferred event cannot pin later events.
- `delivery_id` is stable for one recipient Task; each recipient gets its own delivery ID and its own monotonically increasing `delivery_revision`, which is the sequence number for that recipient's Delivery stream. It is independent of `output_package.version`; the two values may differ. The first `created` (or `ready`) event uses Delivery revision 1. Within a Delivery revision, `created` may transition to `ready`, `accepted`, or `needs_fix`; `ready` may transition to `accepted` or `needs_fix`; and `revised` may transition to `accepted` or `needs_fix`. A replacement Package is represented by `revised` at exactly the next Delivery revision after `needs_fix` or `accepted`; its subsequent response keeps that Delivery revision. Each transition event has a distinct event ID. Receivers deduplicate by event identity, preserve event order within each delivery, reject lower revisions and revision gaps, and validate status transitions within a revision; they must not discard every event whose revision equals the latest revision. A revision gap or invalid transition is quarantined and blocks later lower/equal-order events for that Production, activation epoch, and delivery. Quarantined event IDs remain deduplicated, so recovery requires explicit operator reconciliation rather than blind retry.
- KitsuSync routes only by exact `production_id + recipient_task_type_id` and existing Discord route IDs. Missing/ambiguous route is quarantined with a sanitized diagnostic; no fallback to names or another Production. File-delivery status never changes Kitsu Task WFA/RETAKE/DONE state.
- Initial sync/import is notification-suppressed. Only business transitions created after explicit activation (or an explicitly enabled post-activation setting) are eligible for Discord delivery. Historical discovery never generates a burst of new-delivery messages.
- Event payloads contain IDs and bounded display metadata, never OAuth credentials, webhook URLs/tokens, cookies, public-sharing links, or arbitrary destination URLs. KitsuSync builds Kitsu links from its configured trusted origin and stable IDs. Drive links are emitted only after server-side access-policy checks; public sharing is not part of this contract. Discord content is escaped and uses the existing restricted `allowed_mentions` policy; default is no mentions.
- Event rows and resulting Discord deliveries are durable and independently deduplicated. An HTTP acknowledgment is not a Discord-send acknowledgment. KitsuSync reports its own delivery journal state; it never claims recipient receipt/device push.

## Identity and payload rules

Kitsu identifiers are UUID strings: `production_id`, `episode_id`, `sequence_id`, `entity_id` (`shot` or `asset`), source/recipient `task_id` and `task_type_id`, and `person_id`. Snapshot pages include Task Type metadata rows so every Task's `task_type_id` resolves to a stable Task Type ID. `task_type_name`, entity names/codes, and person display names are descriptive snapshots only. A Task Type rename does not alter route resolution.

Output Packages have a Plugin-owned stable `output_package_id`, positive monotone `version`, `classification`, `manifest_sha256`, bounded manifest reference, and zero or more Drive object IDs with content SHA-256 and byte count. Optional frame range has integer start/end/step and an explicit rate numerator/denominator. Never accept a path, local file name, or URL as object identity. Sender is a Kitsu `person_id` with a display snapshot. A single distribution to multiple Tasks is represented by separate delivery events, not one shared mutable recipient state.

## Integrated use flow

1. A Production administrator opens the native Kitsu Files Plugin settings. The Plugin checks the current Kitsu/Zou role and Production access, performs the server-side OAuth exchange with the existing `openid + drive.file` scopes, selects and verifies an app-visible root, saves templates/configuration with revision fencing, and explicitly activates at a fresh epoch. The Plugin is the only writer for these Drive settings.
2. KitsuSync reads the Plugin's sanitized authority status and configuration mirror. A failed read blocks status display; event intake and dispatch still require the unresolved mirror-freshness integration gate above. KitsuSync does not offer Drive setup, root, template, or activation mutations. Legacy KitsuSync rows remain available for preview and explicit import only; neither a read nor an install silently transfers ownership.
3. For a separately authorized sync operation, KitsuSync obtains a bounded read-only Kitsu/Zou snapshot and submits it to the Plugin. Preview, Apply, retry, and reconcile remain idempotent and are fenced by the Plugin's current configuration revision and activation epoch. The Plugin performs Drive work through existing storage connections, bindings, and workers.
4. The Plugin sends signed events to KitsuSync. KitsuSync durably accepts or quarantines them using the current Plugin activation mirror, then dispatches eligible file-delivery events through the existing Production plus recipient Task Type Discord routes and delivery journal. No Plugin-owned Discord webhook configuration is used.
5. Legacy import is an explicit manager-approved, non-destructive Plugin operation: preview the exact source revisions and verified root; preserve existing credentials, roots, templates, bindings, jobs, and history; import disabled at a fresh epoch; write an immutable audit event; and retain a consistent pre-import backup for rollback. Do not silently switch ownership or mutate Drive objects/ACLs.

## Template materialization semantics

The Plugin template catalog response includes a required `materialization` descriptor (`schema_revision: 1`) for every template. Native Plugin settings select and persist the exact catalog `scope`, `id`, `revision`, and `overrides`; the Plugin resolves those exact immutable catalog entries into its execution tree. KitsuSync does not edit template configuration or synthesize a folder tree. An unknown scope/ID/revision, unsupported override key, or unsafe folder component is rejected before Plugin configuration is committed.

For the v1 default profile, `root_binding` is exactly `verified_root_is_production_root`: the selected, successfully verified Drive root **is the Production folder**. The Plugin never creates or adopts a second folder named after the Production. All static template folders are children of that verified root. A root must be Production-scoped, belong to the selected StorageConnection, and have provider-confirmed child-create permission before Activation. A future “root is parent of Production folder” mode requires a distinct contract value and must not be inferred from a URL or name.

The default materialization is deterministic and folder-only: `00_Production`, `01_Shared_Assets`, `02_Shots`, `03_Editorial`, and `04_Delivery` are stable template-ID children of the Production root. Selected Asset Tasks resolve under `01_Shared_Assets`; selected Shot Tasks resolve under `02_Shots`, optionally through Episode and Sequence when their scope and resolved Kitsu hierarchy include them. Both Asset and Shot branches may be selected together. Each branch resolves its own Task-role node; Working, Publish, Shared Outputs, and Final Delivery are nested beneath the Task. Dynamic folders use Kitsu UUIDs for binding identity. Names are display snapshots and must never be used to adopt or reconnect provider folders.

The Plugin may save a verified connection and root with every hierarchy scope disabled while setup is incomplete. That configuration cannot be previewed or activated. Any enabled hierarchy sync requires Task synchronization plus at least one matching Shot or Asset template and scope; Sequence requires Shot, and Episode requires Sequence. Every enabled entity kind must have its matching selected template. The Plugin enforces this on configuration writes and repeats validation before Preview, Apply, activation, and Worker execution.

`overrides` uses only the keys advertised by that catalog entry's `materialization.available_overrides`. Values replace one folder component; they cannot change role, parent, root, or stable identity. The Plugin rejects path separators, dot segments, control characters, undeclared placeholders, and values that exceed the contract limit. Catalog revision changes are explicit and invalidate stale Preview/Apply work.

Plugin configuration writes atomically store the derived `SharedTemplateConfiguration` execution snapshot with the same Production, connection, verified root and `config_revision`. It remains disabled unless the separately fenced Activation is enabled. Preview, Apply and the Worker all use that persisted snapshot and recheck configuration revision, activation epoch, connection, root, template version and current Kitsu authorization. Existing reserved provider IDs may be reconciled by exact identity; an unbound same-name folder is never adopted. v1 currently permits only `new_production` for new configuration; `future_only` and `adopt_existing` remain rejected until their distinct boundary/proof semantics are specified and tested. Legacy import is a separate, explicit, inactive operation.

See `fixtures/desired-config-adopt-existing.json`, `fixtures/sync-preview.json`, `fixtures/sync-snapshot-start.json`, `fixtures/sync-snapshot-page-0.json`, and the event fixtures for synthetic payload examples. Business-event acknowledgements prove durable intake only; delivery success is read from KitsuSync's delivery journal. The Plugin may send `storage_authority.activation_requested` or `storage_authority.deactivation_requested` alone in a signed request. KitsuSync acknowledges these transitions only after the per-Production dispatch barrier has drained in-flight Discord sends, the new epoch and mirror state have committed durably, and pending old-epoch file deliveries have been durably quarantined. A conflict, database error, or unavailable barrier returns an error and the Plugin remains paused. This guarantee requires the documented single KitsuSync app process to own both the HTTP receiver and delivery dispatcher; deployments that run multiple app processes must remain blocked until the barrier is shared across processes.

## Required state vocabulary

- Connection: `not_configured`, `authorizing`, `connected`, `permission_denied`, `expired`, `revoking`, `revoke_pending`, `error`.
- Root verification: `unverified`, `verified`, `permission_denied`, `not_found`, `wrong_drive`, `error`.
- Sync job: `preview_ready`, `queued`, `running`, `completed`, `failed`, `reconcile_required`, `cancelled`.
- Per-recipient delivery: `created`, `ready`, `accepted`, `needs_fix`, `revised`, plus `blocked_no_route` and `quarantined` on the KitsuSync side.
- Errors are stable machine codes with localized client text; raw provider responses and secrets are not returned.
