# KitsuSync Staging on vfxstudio

Production continues to use the root-installed `kitsusync-deploy` release wrapper, its release provenance policy, the existing Compose project, and loopback port `127.0.0.1:8090`. Staging is a second Compose project named `kitsusync-staging`; it uses the fixed container name `kitsusync-staging`, loopback port `127.0.0.1:8091`, and Docker volume `kitsusync-staging-data`.

Staging mounts its named `/app/data` volume and a root-owned, read-only `/etc/kitsusync-staging/conf.toml` containing only non-secret runtime defaults required for startup. The config is `root:10001` mode `0440`: only root and the app's runtime group can read it. The v7 helper checks that exact metadata and runs a pre-start readability check inside the candidate image as UID/GID `10001:10001`. This config is independent from Production. The candidate image contains its own executable and `tpl` tree; host templates are never mounted. Docker's per-container log stream is separate. SQLite, persisted connection/config state, admin sessions, and the process-generated `runtime-secret.key` live in the staging data volume and are not shared with Production.

The Staging Compose definition disables polling and uses a normal, externally connected Docker bridge so the instance can reach Kitsu/Zou. Before starting Staging, the deploy helper reads only the KITSU_HOSTNAME key from the root-owned Production operator environment at /etc/kitsusync-deploy/.env.local, validates and normalizes that HTTP(S) endpoint, and passes it to the Staging container through a private, transient Compose override. It never copies or prints the Production environment file, Kitsu email/password or bot token, Discord credential/webhook, SQLite, sessions, runtime secret, or other Production state. A missing, duplicate, malformed, or unsafe hostname fails closed before Compose starts. Thus a fresh Staging login page has a trusted authentication authority without accepting browser-supplied hosts. Sign in with an authorized Kitsu user, then configure and test a separate Staging Kitsu bot/principal through Connections. Staging credentials and persisted state remain independent.

Discord polling remains disabled with `KITSUSYNC_DISABLE_POLL=1`. Staging has an independent SQLite/data volume and config; Production Discord credentials and state are neither copied nor mounted, and the helper rejects known Discord credential environment variables in the container. This prevents Production Discord side effects. A dedicated Staging Discord destination can be configured separately in the future.

`kitsusync-staging-bootstrap` installs the root-owned `/usr/local/sbin/kitsusync-staging-deploy`, the isolated Compose definition, and one sudoers entry for `ukyo_vfx` that permits only that helper. The one-time bootstrap bundle is kept at `/var/tmp/kitsusync-staging-bootstrap-<sha>-v2` so an older failed staging attempt cannot be overwritten. The helper accepts one exact 40-character source SHA, reads the matching candidate bundle from `/var/tmp/kitsusync-staging-candidate-<sha>`, rejects symlinks and unexpected files, checks candidate provenance and all recorded file/image digests, validates Docker's loaded image identity, and deploys only project `kitsusync-staging`. It verifies the runtime build identity, Staging-only container/network membership, port binding, exact isolated mounts, polling/Discord environment policy, config readability under the actual non-root image user, health/readiness, and admin routes. Updates snapshot SQLite and the runtime secret before replacement, then restore and verify the previous candidate if the new candidate fails. It snapshots the published container set on 8090 before deployment and fails if that set changes.

The staging-v7 helper upgrade accepts the exact prior staging-v6 helper, preserves the existing Staging config and data, and adds fail-closed derivation of the non-secret Kitsu hostname for fresh and later Staging starts. It reads only KITSU_HOSTNAME from the protected Production operator environment, normalizes that endpoint, and passes it through a root-only transient Compose override.

Production is never selected by the Staging helper. Release deployments remain gated by the existing `kitsusync-deploy` wrapper and are not automated from candidate CI.

## Review tunnels

The per-user Scheduled Task `KitsuSync VFXStudio Review Tunnels` runs one hidden OpenSSH process with `BatchMode=yes`, `ExitOnForwardFailure=yes`, keepalives, and two fixed forwards:

- `127.0.0.1:18090` to vfxstudio `127.0.0.1:8090` (Production)
- `127.0.0.1:18091` to vfxstudio `127.0.0.1:8091` (Staging)

The task ignores duplicate starts and restarts a terminated SSH process. The runner exits without binding if either local port is occupied by anything except the exact expected SSH process.

## Bootstrap and routine candidate workflow

Infrastructure maintenance is a separate, rare path. `scripts/upgrade-kitsusync-staging-helper.ps1 -CommitSha <sha>` verifies exact-SHA CI and Security success, stages the exact helper and its root upgrade script, then performs only the approved Staging helper update through breakglass. It does not deploy the candidate application. Initial bootstrap remains `kitsusync-staging-bootstrap`; neither infrastructure path is called by routine candidate deployment.

Routine deployment is `scripts/deploy-kitsusync-staging-candidate.ps1 -CommitSha <sha>`. It first checks that the installed stable helper advertises the exact `staging-v7` contract. If the helper is missing or outdated, it stops with `STAGING_BOOTSTRAP_REQUIRED` before downloading or uploading candidate files. Otherwise it requires successful CI and Security runs for the exact SHA, downloads that run's immutable candidate artifact into a private temporary directory, verifies the GitHub ZIP digest, candidate provenance, expected file set and recorded file digests, then stages the bundle and invokes only `/usr/local/sbin/kitsusync-staging-deploy <sha>` with `sudo -n`. The routine path never installs or upgrades infrastructure, calls breakglass, or addresses Production. It removes local temporary files and verifies health, readiness, and admin routes through a shared bounded readiness verifier before committing runtime identity.

The installed root helper pins the SHA-256 of `kitsusync-image-identity` and `kitsusync-sqlite-backup` before executing them, because both run with root privileges during image inspection and rollback backup. Changing either tool requires an explicitly reviewed Staging helper upgrade; a routine application candidate cannot replace these root-executed programs.

After this workflow is merged to the default branch, `.github/workflows/staging-deploy.yml` can automatically deploy same-repository pull-request candidates after Security Audit and exact-SHA CI succeed. It runs on a GitHub-hosted Ubuntu runner, uses a short-lived Tailscale OIDC node, checks out only trusted default-branch deployment tooling, and consumes the candidate artifact as validated data. A repository-wide concurrency group cancels superseded runs; the host helper also serializes Staging transactions with a Staging-only lock. The post-start network membership check retries empty Docker network metadata for up to 15 seconds, but rejects unrelated or multiple container IDs immediately and emits bounded ID-prefix and attachment diagnostics on failure. Production has no automatic candidate deployment path.

Automation stays disabled unless repository variable `KITSUSYNC_STAGING_AUTODEPLOY=enabled` is set. One-time setup also needs variables `KITSUSYNC_STAGING_SSH_HOST`, `KITSUSYNC_TAILSCALE_OIDC_CLIENT_ID`, and `KITSUSYNC_TAILSCALE_OIDC_AUDIENCE`; secrets `KITSUSYNC_STAGING_SSH_PRIVATE_KEY` and `KITSUSYNC_STAGING_SSH_KNOWN_HOSTS`; a matching public key for the unprivileged `ukyo_vfx` account; and a Tailscale OIDC/tag policy that allows the ephemeral `tag:github-actions` node to reach only the Staging SSH target. Until configured, the workflow remains skipped and routine operator deployment remains available after helper bootstrap. The vfxstudio machine is never a GitHub Actions runner.

Deployment never promotes a candidate artifact to release identity. Human review occurs on port 18091. Only explicit human acceptance can authorize merge, release, or Production deployment.
